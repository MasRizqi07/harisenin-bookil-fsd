# Bookil operational runbook

The owner executes these procedures. No live credentials, external purchases, bucket operations or restores were performed by the agent. Record the release SHA, time, order number and redacted evidence for each incident. Do not paste keys, raw financial payloads, Authorization headers or signed download URLs into tickets or logs.

| Symptom | Inspect | Action and expected result |
| --- | --- | --- |
| Webhook does not arrive | Midtrans notification URL, sandbox/live account selection, gateway delivery status, TLS and Cloudflare challenge/WAF events | Configure the HTTPS `/webhooks/midtrans` URL in the correct gateway account. Keep the existing CSRF exemption. Avoid browser challenges on server notifications. Ask the gateway to retry, then verify local order/payment state. Do not add a fixed Midtrans IP allowlist in code. |
| Customer paid but order is pending | Customer order number, current Midtrans status and amount, local order/payment records | Run `php artisan bookil:reconcile 'BK-<actual-ulid>'` under the application account. Success prints `pending -> paid`; replay prints `paid -> paid` without a second payment/event. The command fetches signed status and delegates to ProcessPaymentWebhookAction, which rechecks the gateway. Missing signature, amount mismatch or outage exits nonzero. Resolve the mismatch/outage; never update an order to paid manually. |
| Reconciliation exits nonzero | Order existence, configuration/profile, gateway availability; command's check/class label | Retry only after resolving the cause. No secret value or full response is printed. A successful configuration preflight is not proof that gateway credentials work. |
| Customer reports download HTTP 403 | Authentication, ownership, paid state, signed-link expiry/tampering, entitlement date/quota, trusted proxy scheme | Ask the owner of the purchase to sign in and open a fresh order/library page. Check `download_attempts` outcome and client IP without copying the URL. A URL lasts at most 15 minutes; entitlement is initially 30 days/5 grants. Reversal blocks access. For proxy issues, check explicit trusted CIDRs and HTTPS forwarding. Do not bypass policies or remove signed middleware. |
| Download HTTP 429 | User-level 30/minute limiter, Redis shared state and recent denied_throttled audit rows | Wait for the limiter window; investigate abusive requests. Middleware denial rows are deduplicated per actor/item/outcome per 60 seconds. Quota must not increase on middleware denials. Do not reset global counters to bypass unexplained abuse. |
| Download quota exhausted or entitlement expired | Paid order/item, actual usage, previous entitlement extension audit, support reason | Administrator opens `/admin/orders/{id}`, uses **Perpanjang hak unduh**, adds downloads and/or days and supplies a reason. Used downloads are preserved; expiry extends from the later of now and its current value when days are added. One audit records actor, item, deltas, reason and time. Failed/refunded orders cannot be extended. No manual bearer token is created. |
| Refund or chargeback received | Verified gateway status, local payment status, order state, entitlement date | Let the existing webhook/reconcile path apply reversal and expire entitlement. Verify that another download request is denied and no new purchase receipt is generated. Do not reinstate the entitlement until a separate valid purchase exists. Already issued storage URLs may remain usable until their 15-minute expiry; application revocation cannot cancel an existing provider URL. |
| Verification/reset/receipt email absent | Verified sender DNS, SMTP plan limit, credentials managed by owner, mailer selection, failed jobs and Supervisor state | Check SMTP relay connectivity and provider delivery events without logging credentials. Check Redis queue workers, run `php artisan queue:failed`, resolve the cause and retry only the relevant failed job. Receipt messages link to the authenticated order page, never to a signed file URL. Verify sender/mailbox ownership. |
| Audit tables growing | Scheduler cron, `schedule:list`, oldest attempted_at/created_at dates, Redis dedupe behavior | Check daily `model:prune`. Retention is 90 days for download attempts and 180 for webhook notifications. Do not prune payments/orders/items or extension audit records. Run a prune drill on staging before changing retention. |

## Database and asset restore

1. The owner chooses backup frequency, RPO/RTO, off-host encrypted retention and access controls. Back up PostgreSQL and both public covers and private assets, retaining the key mapping and the persistent application encryption key in a separate secret manager.
2. For PostgreSQL, use the owner's existing authenticated connection configuration (for example a restricted `.pgpass` file); never place passwords in shell arguments or evidence. Example backup: `pg_dump --format=custom --file=bookil-backup.dump --dbname=bookil`. Verify the archive with `pg_restore --list bookil-backup.dump` and record its checksum and timestamp.
3. Drill recovery on staging into a **new empty database**: `createdb bookil_restore_drill`, then `pg_restore --no-owner --no-acl --dbname=bookil_restore_drill bookil-backup.dump`. Use owner-approved DB roles; the example is not permission provisioning. Never point this drill at the active database.
4. Restore matching public covers/private object snapshots. R2 has no S3 bucket versioning API; the selected off-host/versioned recovery strategy must preserve deleted/replaced assets. Verify representative object keys and sizes against the restored products. Retain old snapshots; do not overwrite today's bucket during a drill.
5. Run an isolated application instance with the restored database, separate Redis namespace and preserved appropriate environment key. Check migrations, catalogue, owned order views, payment totals, download allowance and actual private downloads. Record row counts, representative checks and elapsed restore time. Disable outgoing live gateway operations during the drill.
6. For an actual incident, stop writes and workers before selecting a restore point. Compare gateway transactions since the backup with local orders. Reconcile affected existing orders through `bookil:reconcile`; missing post-backup orders require owner investigation and reconstruction from verified records, not fabricated payment rows. Resume only after the owner approves the consistency review.

## Midtrans key rotation

The owner controls all keys and the gateway dashboard. First test the rotation procedure using sandbox credentials. Schedule a maintenance/retry window, follow Midtrans's account-specific rotation procedure, provision the new environment through the secret manager, rebuild config cache and gracefully restart queue workers/FPM. Do not print either key. Coordinate webhook retries: signatures generated with a previous key may be rejected after rotation; the status API reconciliation command uses the currently configured key and still requires a signed response. Check pending/recent orders and callback delivery. Retire the old key only according to the provider's procedure and the owner's incident decision.

## Public Git history

The old `taskku` SQLite file is removed from the current tree but remains in public Git history with two password hashes. Treat those hashes as exposed; the owner must rotate the associated passwords wherever reused. Purging history is an owner decision, does not recall existing public clones and was not performed here.
